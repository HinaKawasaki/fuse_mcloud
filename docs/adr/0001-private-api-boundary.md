# ADR-0001：私有接口红线——默认路径不新增任何未封装端点

- 状态：**已接受**
- 日期：2026-10-14
- 决策者：项目维护者
- 相关：[API 能力矩阵与风险登记册](../api-capability-matrix.md)

---

## 背景

`mcloud_FUSE` 的能力瓶颈来自云盘接口，而不是文件系统层。起初的讨论把它表述为
「官方 API 能力有限，使用 Web 端的 API 有风险」，并一度推论「既然已经在调私有接口，
再多调一点也无所谓」。核实上游后，**这两个说法都不成立**。

**第一，我们从未越界。** 官方 Skill 是认证企业「中移互联网」在 SkillHub 上架的公开技能
（`@org-vt43r0t0/cm-cloud-manage`，`ownerId 631940`，2 万+ 下载，有版本历史，
`basement/SKILL.md` frontmatter 标注 `author: 中移互联网`）。请求经 skill 专用适配网关
`orches.yun.139.com/adaptor/new/skill/nk/` 发出，携带注册身份
（`AUTH_SKILL_ID` / `AUTH_DEV_ID` / `AUTH_CLIENT_ID`）；用户侧走标准登录授权页
（`URL_APP_ID` / `URL_APP_KEY`）；v2.x 更迁到 `openapi.yun.139.com/open-ai-space`。
这是**厂商提供的集成通道**，不是抓包得来的私有接口。

**第二，风险不是二元的。** 「已经越界所以再越一点无所谓」混淆了「继承的暴露面」与
「自建的暴露面」。即使前提成立，边际风险仍显著：

| 维度 | 走官方 Skill | 自研 Web / 未授权调用 |
| --- | --- | --- |
| 出问题谁修 | 上游（中移互联网）发版修 | 只有自己，且端点静默失效 |
| 可撤销性 | 换回旧版本即可 | 账号被风控后不可撤销 |
| 行为特征 | 有 `skillId` / `devId` 身份归属 | 无归属，恰是最易被风控识别的部分 |
| 可持续日更 | 可跟版、可写成公开承诺 | 通道随时消失，与可持续直接矛盾 |

**第三，真正的天花板是 Skill 版本，不是 API。** 本项目锁定 v1.0.4，而官方已发布
**v2.0.2**：新增 `file/list`（**专用目录列举端点**，可根治「列举骑在搜索索引上、
天生最终一致」这一最深的问题）、`listUploadedParts`（分片续传）、`batchCopySync` 等。
但删除 / 移动 / 重命名在 v2.0.2 中是**厂商主动注释停用**的，源码注释原文：
「本期场景范围外……不注册路由、不定义调用入口、不发起网络请求」，
并注明「保留原实现供后续明确纳入范围时恢复」。

因此真实的选择是：

> 是**升级到官方 v2.x，拿到厂商愿意给的能力**，
> 还是**绕开厂商一个显式的范围决策，去 Web 端自己取**。

删除不是厂商「忘了做」，而是**明确划在范围外**。绕开它，性质不是「用我们已经在用的
API」，而是**推翻厂商的显式范围决策**——这正是本 ADR 要禁止的事。

## 决策

### 1. 端点白名单

默认路径（即不设置任何额外环境变量时）**只允许**调用
[能力矩阵第 2 节](../api-capability-matrix.md) 登记的 10 个端点。
新增任何端点，必须先更新能力矩阵文档，再写代码。

### 2. L3 端点默认禁止

App / Web 端的其它私有端点不进入默认路径，**明确包括且不限于**：

- 任何删除 / 回收站 / 清空类接口
- 任何真正的移动 / 重命名原语
- 任何账号、配额、分享、登录之外的身份类操作
- 任何绕过现有客户端限流的批量调用方式

### 3. 探索必须隔离且显式

如果将来确有需要验证某个 L3 端点，必须同时满足：

| 要求 | 具体形式 |
| --- | --- |
| 隔离存放 | 独立模块（如 `mcloud_fuse/unofficial/`），默认路径 **import 时不加载** |
| 显式开启 | 需 `MCLOUD_ENABLE_UNOFFICIAL_API=1`，缺省关闭 |
| 显著告警 | 启用时在 stderr 打印风险提示，并写入日志 |
| 诚实标注 | README、`--help`、release notes 均标注 **unsupported / 可能导致账号风险** |
| 不进默认测试 | CI 不测试它（私有接口不可作为构建稳定性依赖） |
| 可一键剥离 | 删除该目录后其余功能不受影响，即无反向依赖 |

### 4. 责任归属

启用 L3 适配器的用户**自行承担账号与数据风险**；项目不在文档中暗示其可用或安全。

### 5. 红线不等于功能停滞

红线约束的是**能力来源**，不约束**更新频率**。
日更应转向修复、文档、测试、兼容性与反馈四类供给（另文展开），
而不是靠加接口来凑。

## 后果

### 正面

- 暴露面被冻结在一份可枚举的清单里，风险可度量、可审计。
- 「官方 Skill 变了怎么办」收敛为 10 个端点的契约测试，而非全盘排查。
- 明确拒绝 L3 之后，「目录改名不支持」「删除不释放容量」等缺口被如实呈现，
  用户预期与实现一致——这是长期信任的来源。
- 为后续「上游跟版」节奏提供了确定的检查范围。

### 负面

- **能力天花板被正式接受**：删除、回收站、目录改名、随机写等将长期缺失。
- 一部分潜在用户会因为没有真正的删除而流失。
- 「每日一更」不能再靠功能驱动，必须建立非功能的更新供给（这是有意的取舍）。

### 中性

- L2 端点的既有风险不因本决策消失，只是**不再增长**。见 R5/R6。

## 备选方案与未采纳理由

| 方案 | 未采纳理由 |
| --- | --- |
| 继续锁 v1.0.4、不升级 | 把「项目没做」误当成「API 做不到」。v2.0.2 的 `file/list` 能根治列举一致性问题 |
| 直接用 Web 端接口补齐删除等能力并默认开启 | 收益是个别语义，代价是账号级风险 + 随时断链；且等于推翻厂商显式范围决策 |
| 只在文档里口头约定「尽量不用」 | 无机制约束，等于没有决策。本 ADR 要求隔离 + 开关 + 告警 |
| 允许只读 Web 接口默认开启 | 只读同样走未授权路径，风控不区分读写；且会稀释「默认安全」的承诺 |

## 配套行动：升级到官方 Skill v2.0.2

红线冻结的是**能力来源**，不是**能力上限**。当前能力不足有一个更简单的解释：
**我们锁定的是 v1.0.4，而厂商已经发到 v2.0.2。**

| v2.0.2 带来的 | 影响的登记册条目 |
| --- | --- |
| `file/list` 专用目录列举端点 | **R1**（列举依赖搜索索引）——有望根治，而非缓解 |
| `listUploadedParts` 分片续传 | 大文件断点续传 |
| `batchCopySync` 同步复制 | 跨目录移动链路简化 |
| 相册 / 故事 / 分享 / 活动等新场景面 | 新的更新供给来源 |
| 新网关 `openapi.yun.139.com/open-ai-space` | 需重新核实端点与鉴权 |

**代价必须说清**：v2.0.2 的 Python 接口是**代际更换**——`cm_cloud_client` /
`cm_cloud_sandbox` / `cm_cloud_transport` / `cm_cloud_format` / `cm_cloud_errors`
在 v2 中**均不存在**，改为 `adapter_*` / `core_*` / `command_*` 架构。
而 `mcloud_fuse/client/wrapper.py` 在 import 期直接依赖上述模块，
因此这**不是改版本号可完成的升级，而是客户端层重写**。

**待厂商放行**：删除 / 移动 / 重命名。v2.0.2 已包含这些实现但被主动注释停用。
正确做法是等待或通过正规渠道请求厂商纳入范围（发版即可用），
而不是自行调用 Web 端等价接口。

## 执行与验证

决策若只写在文档里就会腐烂。落地手段（后续实现，本 ADR 只定义目标）：

1. CI 增加一条检查：除隔离目录外，源码中不得出现能力矩阵白名单之外的
   `personalSaas/`、`aiService/` 等端点字面量。
2. 代码评审清单加入一问：「本次改动是否新增了端点？能力矩阵是否已更新？」
3. 发布检查清单加入：「所依赖 Skill 的版本是否已记录、并按能力矩阵重新核实过？」
   （版本锁定本身已由 CI 的 `MCLOUD_SKILL_VERSION` 承担。）

---

## 复审条件

出现以下任一情况时重新讨论本 ADR：

- 云盘发布**有文档、有版本承诺**的开放 API，届时 L2/L3 概念需要重写。
- 上游 Skill 正式提供删除 / 回收站能力。
- 隔离适配器被实践证明可长期稳定运行，且用户明确愿意承担风险。
